# 텔레그램 알림·원격 지시 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `orch serve` 안에서 텔레그램 봇이 돌면서 사람이 필요한 순간을 휴대폰으로 알리고, 휴대폰에서 버튼·답장·명령으로 스펙 승인, 교착 지침, 건너뛰기, 재개, 상태 조회를 할 수 있게 한다.

**Architecture:** 오케스트레이터 프로세스 안의 `TelegramBot`이 Telegram Bot API를 **long polling**(`getUpdates`)으로 읽는다. PC로 들어오는 연결이 없다. 알림은 기존 `Notifier` 인터페이스를 구현해 이벤트 버스에서 받는다. 사용자 동작은 HTTP 서버와 **같은 직렬화된 동작 계층**(`WorkflowActions`, Task 5)을 통해 `Workflow`에 전달한다. 그래서 대시보드와 텔레그램이 동시에 응답해도 하나만 반영된다. 메시지 형식, 묶음, 조용한 시간, 버튼 데이터는 순수 함수로 분리해 테스트하고, Bot API는 테스트용 가짜 HTTP 서버로 대체한다.

**Tech Stack:** Node ≥ 20 내장 `fetch`·`FormData`·`Blob`(새 의존성 없음), TypeScript ESM, vitest, 기존 fastify·zod.

**Spec:** [docs/scenarios/2026-10-28-user-scenarios.md](../../scenarios/2026-10-28-user-scenarios.md) §3 S4·S5·S7·S8, §4(알림 설계), §5 방안 A, §7 S8 테스트. 상위 스펙: [2026-10-26-agent-orchestrator-design.md](../specs/2026-10-26-agent-orchestrator-design.md) §1.3(2차 텔레그램), §3 Notifier.

## Global Constraints

- 코드 위치: `orchestrator/src/telegram/`(새 폴더), `orchestrator/src/server/actions.ts`(새 파일). 테스트는 `orchestrator/test/telegram/`.
- 비밀값은 환경 변수에서만 읽는다: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. 설정 파일, 이벤트, 로그, 에러 메시지에 토큰을 절대 남기지 않는다(에러·로그 출력 전 `bot<token>` 부분을 `bot***`로 치환).
- 둘 중 하나라도 없으면 봇은 꺼지고(`state: 'off'`) 나머지 시스템은 그대로 동작한다.
- 응답 대상은 `TELEGRAM_CHAT_ID` 한 채팅뿐이다. 다른 채팅의 메시지·버튼은 처리하지 않고 응답도 보내지 않으며, 콘솔에 `텔레그램: 허용되지 않은 채팅 <chat_id>`만 남긴다(설정할 때 chat id를 찾는 용도).
- 텔레그램으로 보내지 않는 것: 원본 프롬프트, 코드 diff, 파일 내용, 봉투 JSON. 캡처는 사용자가 [자세히]를 눌렀을 때만 1장 보낸다.
- 되돌리기 어려운 동작(스펙 승인, 건너뛰기)과 사용량을 쓰는 동작(`/ask`)은 두 단계 확인을 거친다.
- 처리된 알림은 메시지를 수정해 버튼을 없애고 결과 줄(`처리됨 ✓ · <이벤트 ID>` 또는 `이미 처리됨`)을 붙인다.
- 메시지는 평문(`parse_mode` 없음). 길이는 4096자 제한, 넘으면 3900자에서 자르고 `…(대시보드에서 보기)`를 붙인다.
- 설정 기본값(시나리오 §8 제안): 조용한 시간 꺼짐, 생존 신호 꺼짐, 태스크 승인·병합 알림 꺼짐, 무음 묶음 30초.
- Telegram 서버나 네트워크가 실패해도 워크플로는 절대 멈추지 않는다. 알림 실패는 로그만 남긴다.
- 새 npm 의존성을 추가하지 않는다.
- 테스트는 실제 Telegram API를 호출하지 않는다(가짜 Bot API 서버, `apiBase` 주입).

## Review Focus

1. **Telegram API가 내려가거나 네트워크가 끊긴 경우:** polling은 지수 백오프(1s→2s→…최대 60s)로 재시도한다. 보낼 알림 대기열은 최대 100개로 두고, 넘치면 무음 알림부터 버린다. 워크플로 이벤트 발행은 지연되지 않아야 한다. → Task 4, Task 6
2. **봇 토큰이 로그·에러에 새는 경우:** `fetch` 실패 메시지와 HTTP 에러 본문에는 요청 URL이 들어갈 수 있다. 모두 치환 후에만 출력한다. → Task 4
3. **`orch serve` 재시작 시 이미 처리한 업데이트가 다시 오는 경우:** 마지막 `update_id`를 `raw/telegram-offset.json`에 저장해, 같은 `/ask`(사용량 사용)나 답장 지침이 두 번 실행되지 않아야 한다. → Task 6
4. **같은 버튼을 두 번 누르거나 대시보드와 동시에 응답하는 경우:** 먼저 온 것만 반영되고, 나중 것은 "이미 처리됨"으로 끝나야 한다. → Task 5, Task 6
5. **매우 긴 한글 지적 문구·지침, 4096자 초과:** 잘리되 깨지지 않아야 한다(서로게이트 쌍 중간에서 자르지 않음). → Task 2

**Files:**

- Produces:
```ts
export interface OutMessage {
  text: string; silent: boolean
  buttons?: { text: string; callback?: Callback; url?: string }[][]
  kind: 'spec' | 'human' | 'login' | 'error' | 'done' | 'stage' | 'paused' | 'resumed' | 'approved' | 'digest' | 'heartbeat' | 'reply'
  eventId?: string
}
export interface FormatContext { events: Envelope[]; state: RunState; plan: Plan | null; dashboardUrl: string | null; specSummary?: string[] }
export function messageForEvent(e: Envelope, ctx: FormatContext): OutMessage | null   // 알릴 필요 없으면 null
export function statusText(ctx: FormatContext): string            // /status
export function tasksText(ctx: FormatContext): string             // /tasks
export function detailText(eventId: string, ctx: FormatContext): string   // [자세히]
export function reportSummary(reportMd: string | null, ctx: FormatContext): string   // /report, DONE
export function clip(text: string, max?: number /*=3900*/): string   // 서로게이트 안전
```
**알림 규칙(시나리오 §4.1 그대로):**

| 이벤트 | kind | silent | 버튼 |
|---|---|---|---|
| CHAT(from master, `payload.specApprovalRequired`) | spec | false | [승인](approve) [대시보드에서 보기](url, dashboardUrl 있을 때) |
| HUMAN_REQUIRED reason `auth` 또는 `openai_cap` | login | false | [재개](resume) |
| HUMAN_REQUIRED reason `workflow_error` | error | false | [자세히](detail) |
| HUMAN_REQUIRED 그 밖(교착 등) | human | false | [지침 쓰기](guide) [건너뛰기](skip) [자세히](detail) |
| STATE_CHANGE stage `DONE` | done | false | [보고서](report) |
| STATE_CHANGE stage(그 밖) | stage | true | — |
| PAUSED | paused | true | — |
| RESUMED | resumed | true | — |
| APPROVE (notifyTaskApprovals일 때만, 이 함수는 항상 만들고 걸러내기는 Task 3) | approved | true | — |

**문구 형식(첫 줄 고정, 테스트가 확인):**
- human: `🔴 <task> 사람 필요 — <사유 문구>: <마지막 REJECT의 첫 blocker/major 지적 문구>`
- login: `🔴 멈춤 — 터미널에서 다시 로그인 필요` (openai_cap이면 `🔴 멈춤 — OpenAI API 지출 상한($8) 도달`)
- spec: `🟣 스펙 초안 준비됨 — 승인하면 작업을 시작합니다`
- done: `✅ 완료 — 수용 기준 <n>/<m>` (보고서에서 셀 수 없으면 `✅ 완료`)
- stage: `<이전 단계 라벨> → <새 단계 라벨>`, paused: `⏸ 일시정지 — <사유 문구>, <HH:mm> 재개 예정`, resumed: `▶ 재개`

### Task 3: 보내는 곳 — 묶음, 조용한 시간, 밤사이 요약, 생존 신호

**Files:**
- Create: `orchestrator/src/telegram/outbox.ts`
- Test: `orchestrator/test/telegram/outbox.test.ts`

**Interfaces:**
- Consumes: `OutMessage`(Task 2), `TelegramConfig`(Task 1), `Clock`
- Produces:
```ts
export class Outbox {
  constructor(cfg: TelegramConfig, clock: Clock, send: (m: OutMessage) => Promise<void>, opts?: { maxQueue?: number /*=100*/ })
  push(m: OutMessage): void          // 즉시 반환. 내부 타이머로 전송
  flush(): Promise<void>             // 남은 묶음 즉시 전송 (종료 시)
  stop(): void
}
```
**규칙:**
- `approved`는 `cfg.notifyTaskApprovals`가 false면 버린다.
- 소리 알림(silent=false)은 바로 보낸다. 단, 조용한 시간 중이면 silent=true로 바꿔 보내고 "밤사이 목록"에 기록한다.
- 무음 알림은 `batchSeconds` 동안 모았다가 한 메시지로 합친다(줄바꿈으로 연결, kind `digest`). 1개뿐이면 그대로 보낸다.
- 조용한 시간이 끝나는 시각에 밤사이 목록이 있으면 소리 알림 1개: `🌅 밤사이 <n>건 — …`(각 항목 첫 줄).
- `heartbeatMinutes > 0`이면 그 간격으로 무음 `💓 오케스트레이터 동작 중 · <단계>`(단계는 push된 마지막 stage 메시지 기준, 없으면 생략).
