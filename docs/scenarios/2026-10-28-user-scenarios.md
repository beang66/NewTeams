# 사용자 시나리오 — 대시보드와 모바일(텔레그램)

- 작성: 2026-10-28
- 상태: 초안, 사용자 리뷰 대기
- 관련: [스펙](../superpowers/specs/2026-10-26-agent-orchestrator-design.md) · [대시보드 계획](../superpowers/plans/2026-10-27-dashboard.md) · [와이어프레임](../wireframes/dashboard-wireframes.html) · [PRODUCT.md](../../PRODUCT.md)

이 문서는 화면보다 먼저 **"사용자가 언제, 어떤 상태로 들어와서, 무엇을 끝내고 나가는가"**를 정한다. 와이어프레임, 대시보드 구현, 텔레그램 연동은 모두 여기 있는 시나리오를 통과해야 한다. 각 시나리오는 그대로 E2E 테스트 하나가 된다(§6).

---

## 1. 사용자와 사용 장면

**사용자:** 에이전트 파이프라인을 혼자 운영하는 사람. 기획과 개발을 둘 다 이해하고, 터미널을 쓸 줄 안다.

| 장면 | 기기 | 시간 | 하는 일 |
|---|---|---|---|
| 책상 앞, 다른 일을 하며 | 데스크톱 브라우저 탭 | 몇 시간 띄워 둠, 몇 초씩 확인 | 진행 확인, 가끔 개입 |
| 자리를 비움 (회의, 이동, 식사) | 휴대폰 | 알림이 올 때만 | 내 차례인지 판단, 짧은 지시 |
| 처음 맡길 때와 끝났을 때 | 데스크톱 | 10~30분 집중 | 요구사항 대화, 결과 검토 |

**사용자의 시간이 드는 순간은 정해져 있다.** 스펙 승인, 교착, 로그인 만료, 완료 검토의 네 가지다. 나머지는 시스템이 조용히 처리하고, 사용자가 원할 때만 들여다본다.

## 3. 시나리오 상세

### S1. 새 프로젝트를 맡긴다
- **상황:** 만들고 싶은 것이 머릿속에 있다. 아직 문서로 정리하지 않았다.
- **목표:** 대화로 스펙을 정하고 승인한 뒤, 손을 뗀다.

| 단계 | 사용자 | 화면·시스템 |
|---|---|---|
| 1 | `orch new todo-app`, `orch serve todo-app` 실행 | 터미널에 대시보드 주소가 표시된다 |
| 2 | 대시보드를 연다 | 요구사항 화면. 빈 상태 안내: "만들고 싶은 것을 설명해 주세요" |
| 3 | "할 일 앱 만들어 줘"라고 입력 | 마스터가 범위를 좁히는 질문을 한다 |
| 4 | 질문에 2~4번 답한다 | 오른쪽 스펙 초안이 구현 범위, 제외 범위, 수용 기준으로 채워진다 |
| 5 | 초안을 읽고 [스펙 승인] | 화면이 관제로 넘어간다. 텔레그램에 "스펙 승인됨, 기획 시작" 알림(무음) |

- **성공 기준:** 승인까지 10분 이내. 승인 전에는 아무 작업도 시작되지 않는다. 승인 후에는 사람이 다시 할 일이 없다.
- **예외:** 초안이 비어 있으면 승인 버튼이 비활성이다. 서버가 거절하면(이미 승인됨) 그 사유를 화면에 보여 준다. 대화 도중 탭을 닫았다 다시 열면 대화가 그대로 복원된다.

### S2. 맡겨 두고 가끔 확인한다
- **상황:** 다른 작업 중에 탭을 잠깐 연다.
- **목표:** 2초 안에 세 가지 답을 얻고 탭을 닫는다. 진행 중인가, 막혔나, 내 차례인가.

| 단계 | 사용자 | 화면·시스템 |
|---|---|---|
| 1 | 탭을 본다 | 상단 바: 단계 레일의 현재 위치, 주의 0(회색), 사용량 "정상" |
| 2 | (선택) 왼쪽 보드를 훑는다 | 검수 중 1, 반려 1(r2/5), 진행 중 1 |
| 3 | 닫는다 | — |

- **성공 기준:** 주의가 0이면 아무것도 누를 필요가 없다. 화면에 깜빡임이나 큰 움직임이 없다.
- **예외:** 서버 연결이 끊기면 상단에 "연결 끊김 — 다시 연결 중"이 뜬다. 다시 연결되면 빠진 이벤트를 받아와 화면을 맞춘다.

### S3. 자리를 비웠다 돌아와 따라잡는다 *(와이어프레임에 없음 → 추가)*
- **상황:** 2시간 동안 회의를 하고 돌아왔다. 그사이 무슨 일이 있었는지 모른다.
- **목표:** 1분 안에 "그사이 무엇이 끝났고, 무엇이 되돌아갔고, 내가 볼 것이 있는지"를 파악한다.

| 단계 | 사용자 | 화면·시스템 |
|---|---|---|
| 1 | 탭으로 돌아온다 | 상단 바 아래에 **"마지막 확인 이후"** 한 줄 요약: "2시간 전부터 · 승인 3 · 반려 2 · 일시정지 1회(자동 재개됨) · 주의 0" |
| 2 | 요약을 누른다 | 오른쪽 패널에 그 구간의 timeline이 나온다. 구간은 마지막 확인 시점부터 지금까지 |
| 3 | 레인에서 그 구간이 옅게 강조된다 | "확인함"을 누르거나 아무 데나 클릭하면 요약이 닫힌다 |

- **성공 기준:** 이벤트를 하나씩 열지 않고도 요약 한 줄로 따라잡는다.
- **구현 메모:** "마지막 확인 시점"은 브라우저 localStorage에 마지막으로 본 이벤트 ID로 저장한다. 서버 변경은 필요 없다.

### S4. 교착을 푼다
- **상황:** t3이 같은 지적으로 세 번 반려됐고, 마스터 지침으로도 풀리지 않아 사람에게 넘어왔다. 데스크톱에서는 주의 1(빨간 점)로, 휴대폰에서는 텔레그램 알림(소리)으로 알게 된다.
- **목표:** 원인을 이해하고 지침을 보내거나 건너뛴다.

| 단계 | 사용자 | 화면·시스템 |
|---|---|---|
| 1 | [주의 1]을 누른다 | 주의 탭의 카드: 반복된 지적(F-3-1), 마스터가 시도한 지침, 지침 입력란 |
| 2 | (선택) 근거를 본다 | 카드의 [근거 보기] → 상세 [사람용]: 회차 흐름, 지적 표, 캡처 |
| 3 | 지침을 쓰고 [지침 보내기] | 카드가 "보냄 · msg-0061"로 바뀐다. 태스크가 같은 회차를 이어서 다시 진행된다 |
| 3' | 또는 [이 태스크 건너뛰기] → 한 번 더 확인 | 태스크가 '건너뜀'으로 바뀐다. 이 태스크에 의존하는 태스크도 함께 건너뛴다는 안내가 나온다 |

- **성공 기준:** 원인 파악부터 지침 전송까지 3분 이내. 같은 요청에 두 번 응답할 수 없다(먼저 온 응답이 처리되면 나머지 화면에는 "이미 처리됨"이 나온다).
- **예외:** 텔레그램과 대시보드에서 동시에 응답하면 먼저 도착한 쪽만 반영된다. 다른 쪽은 409 응답을 받고 "이미 처리됨"을 표시한다.

### S5. 한도·로그인 때문에 멈춘 것을 처리한다
- **S5-a 사용량 한도(자동):** 상단 배너에 "Claude 사용량 한도 · 14:30 재개 · 남은 시간 1시간 12분"이 뜨고, 텔레그램에 무음 알림이 간다. 사람이 할 일은 없고 주의 수도 늘지 않는다. 재개되면 배너가 사라지고 무음 알림 "재개됨"이 간다.
- **S5-b 로그인 만료(사람 필요):** 주의 카드와 텔레그램 알림(소리)이 온다. 내용은 "터미널에서 다시 로그인 필요"와 로그인 명령 안내다.
  1. 사용자가 PC 터미널에서 로그인한다. 시스템은 비밀번호를 받지 않는다.
  2. 대시보드나 텔레그램에서 [재개]를 누른다.
  3. 작업이 이어지고 카드가 사라진다.
- **성공 기준:** 일시정지와 로그인 만료가 화면에서 구분된다. 자동으로 풀리는 일시정지 때문에 사람을 부르지 않는다.
- **예외:** 로그인하지 않고 [재개]를 누르면 바로 다시 로그인 만료가 되고, 카드 안에 "아직 로그인되지 않았습니다"가 뜬다.

### S6. "왜 이렇게 됐지?"를 추적한다
- **상황:** t3이 유난히 오래 걸렸다. 이유가 궁금하다.

| 단계 | 사용자 | 화면·시스템 |
|---|---|---|
| 1 | 보드에서 t3을 누른다 | 상세 [사람용]: 1회차 검수 반려 → 2회차 하네스 반려 → 3회차 같은 지적 반복 |
| 2 | 2회차의 [원본]을 누른다 | [원본] 탭의 msg-0046: 봉투 JSON과 테스트 출력 |
| 3 | 프롬프트 전문을 본다 | 실제로 개발 에이전트에게 보낸 지시 전체 |
| 3' | 또는 하단 "마스터에게 묻기": "t3이 왜 세 번 걸렸어?" | 마스터가 timeline을 근거로 답하고 메시지 ID를 인용한다. 인용한 ID를 누르면 원본으로 간다 |

- **성공 기준:** 요약 → 근거 → 원본까지 클릭 세 번 이내. 사람용 문서의 모든 결론에 원본 링크가 있다.
- **주의:** "마스터에게 묻기"는 실제 CLI를 호출해 사용량을 쓴다. 입력창 옆에 "사용량을 씁니다"를 작게 표시한다.

### S7. 완료된 결과를 검토하고 공유한다

| 단계 | 사용자 | 화면·시스템 |
|---|---|---|
| 1 | 텔레그램 "완료" 알림(소리)을 받는다 | 요약 세 줄: 수용 기준 7/7, 반려 6회, 소요 시간 + [보고서 열기] |
| 2 | 데스크톱에서 완료 화면을 연다 | 문서 형식의 최종 평가: 그림 1(흐름), 수용 기준별 결과 표, 되돌아간 곳 |
| 3 | 의심 가는 기준의 근거를 누른다 | 해당 캡처와 판정 원본 |
| 4 | 공유한다 | 보고서를 Markdown 또는 인쇄용 PDF로 내보낸다. 원본 프롬프트는 빼고 사람용 문서만 담는다 |

- **성공 기준:** 결과를 믿을 수 있는지 5분 안에 판단한다. "충족"이라고만 적히고 근거가 없는 항목이 없다.
- **와이어프레임에 없음 → 추가:** 내보내기 버튼과 내보내기 범위 안내.

### S8. 휴대폰 알림만으로 대응한다 (텔레그램)
- **상황:** 외출 중이다. PC에서는 `orch serve`가 돌고 있다.
- **목표:** 알림을 보고 내 차례인지 판단한다. 필요하면 휴대폰에서 바로 지시하고 다시 주머니에 넣는다.

| 단계 | 사용자 | 텔레그램 |
|---|---|---|
| 1 | 알림을 받는다(소리) | "🔴 t3 사람 필요 — 같은 지적 반복: 새로고침 후 완료 상태가 사라짐" + 버튼 [지침 쓰기] [건너뛰기] [자세히] |
| 2 | [자세히] | 같은 메시지 아래에 반복된 지적, 마스터가 시도한 것, 최근 캡처 1장 |
| 3 | [지침 쓰기] | 봇이 "이 메시지에 답장으로 지침을 보내 주세요"라고 묻는다(답장 강제) |
| 4 | 답장: "localStorage 키를 todos-v2로 바꾸고 이전 데이터는 무시해도 됨" | 봇: "보냄 · msg-0061 · t3 4회차 시작". 원래 알림의 버튼이 사라지고 "처리됨 ✓"로 바뀐다 |
| 5 | (나중에) `/status` | 단계, 진행 중 태스크, 주의 수, 일시정지 여부를 한 메시지로 |

- **성공 기준:** 대시보드를 열지 않고 1분 안에 교착을 처리한다. 같은 알림의 버튼을 두 번 눌러도 한 번만 반영된다.
- **예외:** PC가 꺼졌거나 `orch serve`가 멈춰 있으면 봇이 응답하지 않는다(봇은 PC에서 돈다). 이 경우 알림 자체가 오지 않으므로, 봇은 30분마다 보내는 무음 "생존 신호"를 설정으로 켤 수 있게 한다(기본 꺼짐).

## 4. 텔레그램 알림 설계

### 4.1 무엇을, 어떻게 알리나
"개입은 드물고 분명하게" 원칙에 따라 **소리 알림은 사람이 필요할 때만** 보낸다.

| 이벤트 | 알림 | 내용 | 버튼 |
|---|---|---|---|
| 스펙 초안 준비됨(INTAKE 중 첫 specDraft) | 🔔 소리 | 구현 범위 요약 3줄 | [승인] [대시보드에서 보기] |
| HUMAN_REQUIRED · 교착 | 🔔 소리 | 태스크, 반복된 지적, 시도한 것 | [지침 쓰기] [건너뛰기] [자세히] |
| HUMAN_REQUIRED · 로그인 만료 / API 상한 | 🔔 소리 | 원인과 해야 할 일 | [재개] |
| HUMAN_REQUIRED · 워크플로 오류 | 🔔 소리 | 오류 요약 한 줄 | [자세히] |
| 완료(DONE) | 🔔 소리 | 수용 기준 충족 수, 반려 수, 소요 시간 | [보고서] |
| 단계 전환 | 🔕 무음 | "기획 → 개발 · 태스크 5개" | — |
| 일시정지 / 재개 | 🔕 무음 | 사유와 재개 예정 시각 | — |
| 태스크 승인·병합 | 기본 꺼짐 | 설정으로 켜면 무음으로 10분 단위 묶음 | — |

- **묶음:** 무음 알림은 30초 안에 연달아 오면 한 메시지로 합친다. 소리 알림은 묶지 않는다.
- **조용한 시간:** 설정(`telegram.quietHours`, 예: 23:00~07:00)에 들어오는 소리 알림은 무음으로 보내고, 조용한 시간이 끝나면 "밤사이 요약"을 한 번 보낸다.
- **보내지 않는 것:** 원본 프롬프트, 코드 diff, 파일 내용. 텔레그램 서버에 저장되기 때문이다. 캡처는 [자세히]를 눌렀을 때만 1장 보낸다.

### 4.2 명령
| 명령 | 동작 | 사용하는 기존 API |
|---|---|---|
| `/status` | 단계, 진행 중·반려·주의 수, 일시정지 | `GET /api/state` |
| `/tasks` | 태스크 보드 요약(그룹별) | `GET /api/state`, `/api/plan` |
| `/ask <질문>` | 마스터에게 묻기(사용량 씀, 확인 버튼 후 실행) | `POST /api/ask` |
| `/resume` | 로그인 만료나 API 상한 뒤 재개 | `POST /api/resume` |
| `/report` | 완료 보고서 요약 + 대시보드 링크 | `GET /api/human/report.md` |
| 알림에 답장 | 지침으로 전송 | `POST /api/human/:eventId` |

서버 쪽에 새 API는 필요 없다. 텔레그램 어댑터는 오케스트레이터 안에서 `Notifier`(이미 있음)를 구현하고, 명령은 HTTP를 거치지 않고 같은 `Workflow` 메서드를 직접 부른다.

## 5. 모바일로 확인하고 지시하는 방안

### 방안 A. 텔레그램 봇 (추천, 1순위)
- **구조:** PC에서 도는 `orch serve` 안의 어댑터가 Telegram Bot API의 **long polling**(`getUpdates`)으로 메시지를 받는다. 외부에서 PC로 들어오는 연결이 없으므로 포트를 열거나 터널을 둘 필요가 없다.
- **보안**
  - 봇 토큰은 환경 변수 `TELEGRAM_BOT_TOKEN`에서만 읽는다(OpenAI 키와 같은 규칙).
  - 응답하는 채팅은 `TELEGRAM_CHAT_ID` 허용 목록 하나뿐이고, 그 밖의 메시지는 무시하고 기록만 남긴다.
  - 건너뛰기처럼 되돌리기 어려운 동작은 두 단계로 확인한다.
  - 버튼 데이터에는 이벤트 ID와 동작만 넣는다. 처리 뒤에는 메시지를 수정해 버튼을 없앤다.
- **장점:** 추가 앱이나 서버가 필요 없다. 알림, 버튼, 답장이 자연스럽고, 스펙에서 2차로 이미 정한 채널이다.
- **한계:** 볼 수 있는 정보가 요약 수준이다. 레인이나 원본을 보려면 데스크톱이 필요하다.

### 방안 B. 휴대폰에서 대시보드 직접 열기 (선택, 2순위)
- **구조:** 대시보드는 이미 모바일 폭(시간순 목록, 주의 카드)을 지원한다. 문제는 서버가 `127.0.0.1`에만 바인딩된다는 점이다.
- **권장 경로:** Tailscale(개인 VPN)로 PC와 휴대폰을 같은 사설망에 두고 `tailscale serve`로 4317 포트를 내 기기들에만 공개한다. 서버 코드는 바꾸지 않는다.
- **하지 말 것:** 공개 터널(예: 인증 없는 Cloudflare 임시 주소)로 내보내기. 대시보드에는 로그인이 없어서 주소를 아는 누구나 지침을 보내고 작업을 건너뛸 수 있다.
- **장점:** 원본과 캡처까지 휴대폰에서 볼 수 있다.
- **한계:** Tailscale 설치와 설정이 필요하다. 알림은 텔레그램이 맡아야 한다.

### 방안 C. 둘 다 (최종 형태)
텔레그램 알림의 [대시보드에서 보기] 버튼이 Tailscale 주소의 해당 화면(예: `/tasks/t3`)을 연다. 알림은 텔레그램, 깊은 확인은 모바일 대시보드가 맡는다.

### 추천 도입 순서
1. **텔레그램 알림과 버튼(방안 A):** S4, S5, S7, S8을 휴대폰에서 끝낼 수 있게 된다. 대시보드 계획과 별개로 오케스트레이터 쪽만 구현한다.
2. **대시보드 구현 마무리:** 모바일 폭이 이미 계획에 들어 있다.
3. **Tailscale 안내 문서 + 알림의 대시보드 링크(방안 C):** 코드 변경은 링크 생성뿐이다.
