# 화면 통합 기준

> 대상: 이전 `NewTeam-main`의 업무 관리 UI와 현재 `orchestration-platform` 관제 UI  
> 기준일: 2026-10-28  
> 목적: 프로젝트 시작부터 실행 관제, 산출물·근거 확인까지 하나의 제품 흐름으로 통합한다.

## 1. 통합 원칙

통합 화면의 기준 구조는 **프로젝트 중심 셸 + 실행 상세 관제**다.

- 이전 UI에서 프로젝트, 작업 시작, 작업 팩 설정, 지식, 산출물 탐색 흐름을 가져온다.
- 현재 UI의 요구사항 대화, 스펙 승인, 파이프라인 개요, 실시간 관제, 사람 개입, 증거 추적, 완료 보고를 실행 상세의 표준으로 유지한다.
- 같은 개념을 두 화면에 중복 구현하지 않는다. 표시 이름만 다른 경우 현재 작업 팩 계약의 용어로 통일한다.
- 완료·승인·실패 표시는 근거 없이 단독으로 표시하지 않는다.
- 화면에서 발생하는 모든 변경 동작은 HTTP와 Telegram이 공유하는 `WorkflowActions`를 사용한다.
- 로컬 1인 운영을 기본값으로 유지한다. 사용자·권한 UI는 다중 사용자 제품화가 결정되기 전까지 가져오지 않는다.

### 5초 판독 기준

어떤 주요 화면에서도 사용자가 5초 안에 다음 다섯 가지를 답할 수 있어야 한다.

1. 지금 어느 프로젝트인가?
2. 실행은 어느 단계인가?
3. 무엇이 진행 중이거나 막혀 있는가?
4. 지금 내가 해야 할 일이 있는가?
5. 비용과 핵심 근거는 어디서 확인하는가?

하나라도 답할 수 없으면 정보구조 검수에서 실패다.

## 2. 개념 통합 규칙

| 이전 UI 개념 | 통합 후 표준 개념 | 기준 |
|---|---|---|
| 앱·에이전트 팀 | 작업 팩 `WorkPack` | 팩 id/version, 입력 스키마, 역할, 태스크 청사진, 검수 기준을 한 단위로 다룬다. |
| 작업·실행 | 실행 `Run` | 프로젝트에 속하며 시작 당시 작업 팩 버전을 고정한다. |
| 단계 `Step` | 태스크 `Task` | 같은 실행 안에서 DAG 의존 관계를 갖는다. |
| 결과 파일 | 산출물 `Artifact` | 반드시 실행과 태스크에 연결한다. |
| 출처·테스트·캡처·판정 | 근거 `Evidence` | criterion id와 관찰 시점, 원본 URI를 갖는다. |
| 실행 기록·운영 로그 | 실행 타임라인 | 별도 상위 메뉴로 중복하지 않고 실행 상세에 통합한다. |
| 역할별 모델 설정 | 작업 팩 설정 | 실제 비밀값은 환경 변수에 두고 UI에는 provider/model 참조만 둔다. |
| 고정 역할 흐름도 | 실제 태스크 DAG | 선언된 역할 장식이 아니라 현재 실행의 실제 의존과 상태를 표시한다. |

관계의 기준 원본은 `orchestrator/src/workpacks/model.ts`와 `contract.ts`다. 화면 전용 복제 타입을 새로 만들지 않는다.

## 3. 정보구조와 내비게이션

### 3.1 전역 셸

데스크톱의 1차 내비게이션은 최대 다섯 개로 제한한다.

1. **프로젝트** — 프로젝트 목록, 생성, 보관
2. **작업 시작** — 프로젝트와 작업 팩 선택, 입력, 실행 전 확인
3. **지식·자료** — 프로젝트 자료, 검색 테스트, 출처 상태
4. **작업 팩** — 역할·모델·입력·검수 기준 설정
5. **설정** — 모델 provider 참조, Telegram 연결 상태, 로컬 실행 환경

전역 셸에는 항상 다음이 보인다.

- 현재 프로젝트 전환기
- 실행 중·사람 확인 필요 개수
- Telegram 연결 상태
- 모델/API 사용량 요약

`실행 기록`과 `운영`은 별도 1차 메뉴로 두지 않는다. 프로젝트 상세의 실행 목록과 각 실행의 관제·타임라인으로 흡수한다.

### 3.2 프로젝트 상세

프로젝트 상세는 다음 순서로 구성한다.

- 프로젝트 이름, 상태, 설명, 기간
- **새 실행** 기본 행동
- 사람 확인이 필요한 실행
- 진행 중 실행
- 최근 완료 실행
- 프로젝트 지식·자료
- 최근 산출물

예산·클라이언트·멤버·이미지 좌표 댓글은 선택 확장 정보다. 현재 로컬 1인 사용의 핵심 흐름을 밀어내지 않는다.

### 3.3 실행 상세

현재 대시보드 화면을 실행 상세의 기준으로 사용한다.

| 실행 상태 | 기본 화면 | 보조 화면 |
|---|---|---|
| `INTAKE` | 마스터 대화 + 스펙 초안 | 프로젝트 자료 참조 상태 |
| 진행 중 | 파이프라인 개요 | 관제, 주의, 태스크, 타임라인, 사람용/원본 상세 |
| `HUMAN_REQUIRED` | 필요한 결정과 영향 범위 | 반복 지적, 근거, 원본 이벤트 |
| `PAUSED` | 중단 사유와 재개 조건 | 사용량·리셋 시각·Telegram 상태 |
| `DONE` | 최종 보고서 | 관제 기록, 산출물, 근거, 원본 |

실행 상세의 상위 탭은 `개요 / 관제 / 산출물·근거 / 보고서`로 제한한다. 상태에 맞지 않는 탭은 숨기지 말고 비활성 사유를 설명한다.

## 4. 이전 화면에서 가져올 것과 제외할 것

| Before | After | Why |
|---|---|---|
| 홈·프로젝트·실행 기록·운영이 각각 실행 정보를 표시 | 프로젝트 상세에 실행 목록, 실행 상세에 관제·타임라인 통합 | 같은 상태의 중복 표현과 이동 비용을 없앤다. |
| 에이전트 팀을 별도 앱처럼 생성 | 버전이 있는 작업 팩으로 생성·복제·설정 | 현재 코어 계약과 실행 재현성을 유지한다. |
| 역할 노드를 고정된 연결선으로 표시 | 실제 태스크 DAG와 현재 상태를 표시 | 선언된 팀 모양보다 실제 실행 경로가 중요하다. |
| 이전 `RunPage`와 현재 관제 화면이 각각 실행 상세 제공 | 현재 관제 화면을 기준으로 파일·터미널·브라우저·산출물 기능 흡수 | 실행 상태와 변경 동작의 원본을 하나로 유지한다. |
| 모델 provider와 API 키를 같은 UI에서 저장 | provider/model 참조만 UI에서 선택, 비밀값은 환경 변수 | 현재 보안 정책과 충돌하는 키 저장을 막는다. |
| 결과 파일 목록만 표시 | 산출물에서 생성 태스크·검수 기준·근거·원본 이벤트까지 이동 | ‘파일이 있다’와 ‘승인된 결과다’를 구분한다. |
| 이모지와 색상으로 상태를 주로 구분 | 텍스트·아이콘·형태를 기본으로 하고 색상은 보조 | 색각·스크린리더·저채도 환경에서도 의미를 유지한다. |
| 모든 프로젝트 업무를 한 화면에 많이 노출 | 현재 목적에 필요한 정보부터 점진적으로 공개 | 장시간 관제 시 인지 부하를 줄인다. |

이번 통합에서 제외한다.

- 이전 Python/LangGraph 실행 상태를 위한 별도 화면
- DB에 API 키를 저장하는 입력 UI
- 현재 코어에 없는 가짜 진행률과 예상 완료 시각
- 실제 실행과 무관한 고정 역할 연결선
- 사용자·권한 관리 화면의 즉시 이식
- 실행 기록과 관제 타임라인의 중복 메뉴

## 5. 화면별 필수 합격 기준

### 5.1 프로젝트 목록·상세

- 프로젝트 카드는 상태, 진행 중 실행 수, 사람 확인 필요 수, 최근 변경 시각을 보여준다.
- 프로젝트를 바꾸면 모든 하위 화면의 범위가 동시에 바뀐다.
- 삭제되거나 접근 불가능한 프로젝트 id는 안전하게 해제한다.
- 빈 상태에는 설명보다 `프로젝트 만들기` 행동을 먼저 제공한다.
- 프로젝트 삭제는 대상, 포함 데이터, 복구 불가 여부를 확인한 후 실행한다.

### 5.2 작업 시작

- 순서는 `프로젝트 → 작업 팩 → 입력 → 실행 전 확인 → 시작`으로 고정한다.
- 작업 팩 카드에는 적합한 용도, 필요한 입력, 예상 산출물, 검수 기준을 표시한다.
- 웹앱, 리서치·리포트, 콘텐츠 캠페인, IP 사업 기획이 같은 화면 패턴을 사용한다.
- 팩별 입력은 해당 Zod 입력 스키마에서 생성하며 별도 수기 타입을 만들지 않는다.
- 시작 전 화면에서 작업 팩 id/version과 사람 승인 지점을 확인할 수 있다.
- 시작 요청을 두 번 눌러도 실행이 중복 생성되지 않는다.

### 5.3 작업 팩 설정

- 역할 이름·목표·추가 지침·provider/model 참조를 편집할 수 있다.
- 태스크 DAG, 필수 산출물, 검수 조건을 읽을 수 있다.
- 고급 설정은 기본 흐름에서 접어 두되 현재 적용값을 요약한다.
- 저장 전 실제 입력 예제로 계약 검사를 수행하고 중복 태스크, 없는 역할·의존, 순환을 표시한다.
- 팩 수정은 기존 실행의 고정 version을 바꾸지 않고 새 version을 만든다.

### 5.4 요구사항·스펙 승인

- 대화와 생성된 스펙을 동시에 볼 수 있다.
- IME 조합 중 Enter는 전송하지 않고, `Shift+Enter`는 줄바꿈이다.
- 승인 버튼은 유효한 초안이 있을 때만 활성화된다.
- 승인 중에는 중복 요청을 막고 성공·충돌·실패를 구분한다.
- 승인 결과의 이벤트 id와 다음 단계가 보인다.

### 5.5 관제·사람 개입

- 현재 단계, 실행 중 태스크, 막힌 태스크, 사람 확인 필요, 비용이 첫 화면에 보인다.
- `HUMAN_REQUIRED`는 전역 배지와 실행 화면 양쪽에 나타나되 같은 요청을 중복 카드로 만들지 않는다.
- 행동 버튼은 `보냄`, `적용됨`, `완료됨`, `이미 처리됨`, `실패`를 구분한다.
- 건너뛰기는 영향을 받는 의존 태스크를 실행 전에 표시한다.
- 원본 이벤트는 사람용 설명에서 한 번의 동작으로 열 수 있다.
- 연결이 끊겨도 마지막 확인 상태를 유지하고 재연결 중임을 명시한다.

### 5.6 산출물·근거

- 산출물은 실행, 태스크, 종류, 생성 시각, media type을 표시한다.
- 근거는 criterion, 종류, 관찰 시각, 원본 URI를 표시한다.
- `승인됨`은 필수 산출물과 팩별 근거 검사가 모두 통과한 경우에만 쓴다.
- 리포트 출처, 웹앱 테스트·캡처, 콘텐츠 권리 검토, IP 권리·재무 검토를 각각 다른 근거 유형으로 보여준다.
- 누락된 근거는 빈칸이 아니라 필요한 항목과 해결 행동을 표시한다.
- 파일 경로는 작업 디렉터리 밖으로 이동할 수 없다.

### 5.7 완료·보고

- 기본 화면은 사람용 최종 보고서다.
- 보고서의 핵심 주장마다 관련 승인·근거·원본 이벤트로 이동할 수 있다.
- 관제 화면으로 돌아가도 선택한 원본 위치를 유지한다.
- 다운로드 파일은 서버가 제공한 보고서 내용만 포함하며 프롬프트·비밀값을 포함하지 않는다.

## 6. 시각 언어

현재 대시보드의 토큰을 기준 원본으로 사용한다.

- 배경 `#010102`, surface 4단계, 1px hairline으로 깊이를 만든다.
- accent `#5e6ad2`는 현재 선택, focus, 주 행동에만 쓴다.
- 성공·경고·실패 색은 반드시 텍스트와 아이콘을 함께 쓴다.
- 기본 본문은 Pretendard/Inter, id·이벤트·토큰은 JetBrains Mono를 쓴다.
- 기본 spacing은 4px 배수, 카드 radius는 6/8/12px만 쓴다.
- 관제 화면은 밀도 높은 dark surface, 최종 보고서와 긴 문서는 paper surface를 허용한다.
- primary action은 한 화면 구역마다 하나만 둔다.
- 긴 한국어, 긴 프로젝트명, 200개 태스크, 10,000개 이벤트에서도 레이아웃이 깨지지 않아야 한다.

## 7. 상호작용과 모션

전문 관제 도구의 모션은 빠르고 조용해야 한다. 장식보다 상태 설명과 즉시 반응을 우선한다.

| Before | After | Why |
|---|---|---|
| 모든 전환에 공통 `200ms` 사용 | 속성별 transition을 선언하고 빈번한 전환은 0~160ms | 사용 빈도가 높을수록 애니메이션이 작업을 늦춘다. |
| 키보드로 여는 화면도 이동 애니메이션 | 키보드 시작 동작은 즉시 전환 | 반복 조작의 연결감을 유지한다. |
| 버튼에 눌림 피드백 없음 | `:active { transform: scale(.97) }`, 100~160ms | 입력이 접수됐음을 즉시 느끼게 한다. |
| hover가 터치 장치에도 남음 | `@media (hover: hover) and (pointer: fine)`에서만 hover | 터치의 고착 hover를 막는다. |
| 패널·popover가 중앙에서 확대 | trigger 기준 `transform-origin`, 모달만 중앙 | 공간적 원인을 설명한다. |
| 새 이벤트마다 눈에 띄는 등장 애니메이션 | 실시간 타임라인은 즉시 추가, 최초 빈 상태 전환만 짧은 fade | 장시간 관제의 시각 소음을 줄인다. |
| `transition: all` 또는 layout 속성 애니메이션 | transform·opacity·색상만 명시적으로 전환 | 레이아웃 재계산과 프레임 저하를 막는다. |
| 기본 easing만 사용 | enter/exit은 `cubic-bezier(.23,1,.32,1)`, 이동은 `cubic-bezier(.77,0,.175,1)` | 즉시 반응하면서 자연스럽게 멈춘다. |
| 모션 감소에서 모든 변화 제거 | 위치·scale은 제거하고 opacity·색상 피드백은 유지 | 멀미를 줄이면서 상태 이해를 보존한다. |

허용 시간:

- 버튼 눌림: 100~160ms
- tooltip·작은 popover: 125~180ms
- select·dropdown: 150~220ms
- drawer·오른쪽 패널: 180~250ms
- toast: 180~240ms, exit이 enter보다 빠름
- 모든 반복 UI 전환: 300ms 미만

## 8. 접근성과 반응형

- WCAG 2.2 AA를 기준으로 본문 대비 4.5:1, 큰 글자와 UI 경계 3:1 이상을 유지한다.
- 모든 행동은 키보드로 가능하고 focus가 항상 보인다.
- 탭·패널·단계는 `aria-selected`, `aria-controls`, `aria-current`를 올바르게 연결한다.
- 경고·요청·오류는 색상만으로 구분하지 않으며 필요한 경우 `role="alert"` 또는 live region을 사용한다.
- 모바일 touch target은 최소 44×44px다.
- 768px 이하에서는 레인 그래프 대신 가상화된 타임라인을 기본으로 사용한다.
- 오른쪽 패널은 모바일에서 전체 폭 drawer가 되며 열릴 때 focus를 이동하고 닫힐 때 trigger로 복귀한다.
- 모바일의 1차 내비게이션은 최대 4개 항목과 `더보기`로 축약한다.
- `prefers-reduced-motion`에서는 이동·scale 모션을 제거한다.
- 200% 확대와 320px 폭에서 가로 스크롤 없이 핵심 행동을 수행할 수 있어야 한다.

## 9. 상태·예외 처리 기준

모든 주요 화면은 다음 상태를 명시적으로 설계하고 테스트한다.

- 최초 loading과 부분 loading
- 데이터 없음
- 서버 연결 끊김과 재연결
- SSE 재연결 후 중복 이벤트
- 이미 처리된 승인·응답
- 두 탭에서 같은 행동을 동시에 실행한 충돌
- 사용량 한도·인증·API 상한 pause
- Telegram 꺼짐·연결 중·연결됨·실패
- 필수 산출물·근거 누락
- 긴 이름·긴 메시지·빈 값·잘못된 파일 경로
- 200개 태스크와 10,000개 이벤트
- 작업 팩 버전 불일치
- 읽기 전용 산출물과 다운로드 실패

오류 메시지는 `무엇이 실패했는지 / 현재 데이터가 보존됐는지 / 사용자가 할 수 있는 다음 행동`을 포함한다.

## 10. 성능 기준

- 로컬 warm load에서 2초 안에 현재 프로젝트와 실행 상태를 조작할 수 있어야 한다.
- 사용자 입력 후 100ms 안에 시각적 접수 상태를 보여준다.
- 수신된 SSE 이벤트는 1초 안에 화면에 반영한다.
- 10,000개 이벤트는 전체 DOM 렌더링 없이 가상화한다.
- 새 이벤트 수신이 현재 사용자의 스크롤·선택·입력 focus를 빼앗지 않는다.
- 애니메이션은 transform·opacity 중심으로 유지하며 긴 task에서 프레임 저하를 만들지 않는다.
- 이미지·보고서·원본 로그는 필요할 때 불러오고 관제 첫 화면을 막지 않는다.

## 12. 통합 순서와 단계별 게이트

### Gate A — 셸과 용어

- 프로젝트 중심 내비게이션과 route가 동작한다.
- `앱/팀/step/result` 용어가 `작업 팩/태스크/산출물·근거`로 통일된다.
- 현재 관제 화면의 회귀 테스트가 모두 통과한다.

### Gate B — 프로젝트와 작업 시작

- 프로젝트 목록·상세, 팩 선택, schema 기반 입력, 실행 전 확인이 연결된다.
- 중복 시작과 팩 version 고정이 검증된다.

### Gate C — 자료와 산출물

- 프로젝트 지식·자료와 실행 산출물·근거가 연결된다.
- 승인된 산출물과 미검수 산출물을 명확히 구분한다.

### Gate D — 작업 팩 설정

- 역할·model 참조·DAG·검수 기준을 편집하고 계약 검사할 수 있다.
- 비밀값은 UI 저장 범위에 들어오지 않는다.

### Gate E — 품질 검수

- UI-01~UI-14를 통과한다.
- 접근성 자동 검사와 키보드 수동 검사를 통과한다.
- desktop/tablet/mobile 실제 캡처를 검토한다.
- 자주 쓰는 동작의 모션을 다음 날 다시 검토한다.

앞 Gate가 통과하기 전에 뒤 Gate 기능을 넓히지 않는다. 화면을 먼저 많이 복사하는 것보다 중복 개념과 상태 원본을 먼저 제거하는 것이 통합 비용이 낮다.

## 13. Definition of Done

화면 통합은 다음 조건을 모두 만족할 때 완료다.

- 하나의 프로젝트 셸에서 생성·시작·관제·근거·보고까지 이동할 수 있다.
- 프로젝트, 실행, 태스크, 산출물, 근거의 화면 관계가 코어 계약과 일치한다.
- HTTP·Telegram·UI가 같은 변경 동작과 충돌 규칙을 사용한다.
- 완료·승인 표시가 검수 근거와 연결된다.
- 이전 UI의 핵심 업무 기능은 보존되고 중복 실행 화면은 제거된다.
- 현재 관제·요구사항·완료 시나리오가 회귀하지 않는다.
- 접근성, 반응형, 성능, 모션, 오류 상태 기준을 통과한다.
- 실제 모델 호출 없이 가능한 UI 테스트와 가짜 서버 테스트가 모두 통과한다.
- 실제 외부 서비스 확인이 필요한 항목은 별도 승인·체크리스트로 분리된다.
