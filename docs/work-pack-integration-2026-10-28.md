# 작업 팩 통합 기록 (2026-10-28)

## 결론

현재 TypeScript 오케스트레이터를 실행 코어로 유지하고, 이전 `NewTeam-main`의 업무 개념만 작업 팩으로 선별 이식했다. Python/LangGraph 실행 엔진, API 키 저장, 고정 순차 실행은 가져오지 않았다.

요청한 순서대로 다음을 완료했다.

1. `프로젝트 → 실행 → 태스크 → 산출물·근거` 관계와 작업 팩 계약 정의
2. 이전 프로젝트의 리서치·리포트 팀 이식
3. 웹앱과 리포트의 서로 다른 검수 기준 교차 검증 후 콘텐츠·IP 기획 팩 확장

## 1. 공통 관계와 계약

관계는 다음과 같이 고정했다.

- 프로젝트 하나는 여러 실행을 가질 수 있다.
- 실행은 시작 시 작업 팩 `id`와 `version`을 고정한다. 이후 팩이 바뀌어도 과거 실행의 판정 기준은 바뀌지 않는다.
- 실행 하나는 태스크 DAG, 산출물, 근거를 소유한다.
- 태스크 의존은 같은 실행 안에서만 허용한다.
- 산출물은 정확히 하나의 실행과 태스크에 속한다.
- 근거는 정확히 하나의 실행과 태스크에 속하며, 필요할 때 산출물 하나를 참조한다.
- 산출물 경로는 실행 디렉터리 안의 상대 경로만 허용한다.

공통 검사는 중복 id, 없는 프로젝트·실행·태스크·산출물, 다른 실행 참조, 없는 의존, 의존 순환, 필수 산출물 누락과 media type 불일치를 잡는다.

작업 팩은 다음을 제공한다.

- 식별자·버전·분야·설명
- 입력 스키마와 비밀값 없는 예제 입력
- 역할 프로필
- 입력으로부터 생성되는 태스크 DAG 청사진
- 태스크별 수용 기준과 필수 산출물
- 분야별 결정론적 검수 함수

관련 코드:

- `orchestrator/src/workpacks/model.ts`
- `orchestrator/src/workpacks/contract.ts`

## 2. 리서치·리포트 팀 이식

이전 프로젝트의 역할과 의도를 다음 DAG로 옮겼다.

```text
조사 계획
├─ 근거 자료 조사 ─┐
└─ 웹 공백 보완 ───┴─ 보고서 작성 ─ 독립 검증
```

이식한 역할은 계획 담당, 조사 담당, 웹 탐색 담당, 작성 담당, 검증 담당이다. 고정 순차 실행 대신 조사와 웹 탐색을 병렬화할 수 있게 했다.

리포트 승인 조건:

- 출처 노트와 최종 보고서, 독립 검증 보고서가 존재한다.
- 입력에서 정한 최소 수 이상의 서로 다른 `http(s)` 출처가 있다.
- 출처는 제목과 확인 시점이 있는 근거 레코드로 남는다.
- 최종 보고서에 모든 필수 섹션과 최소 인용 수가 기록된다.
- 독립 검증 판정이 `approve`이고 미해결 주장이 0개다.

관련 코드: `orchestrator/src/workpacks/builtins/researchReport.ts`

## 3. 같은 코어, 다른 검수 기준

네 팩 모두 같은 관계 검사, 인스턴스 생성, 필수 산출물 검사와 최종 판정 함수를 사용한다. 분야별 기준만 다르다.

| 작업 팩 | 핵심 산출물 | 통과에 필요한 고유 근거 |
|---|---|---|
| 웹앱 | 구현 계획, 소스 변경, 테스트 보고서 | 모든 명령 종료 코드 0, 요청된 브라우저 시나리오, 독립 코드 검수 승인 |
| 리서치·리포트 | 조사 계획, 출처 노트, 최종 보고서, 검증 보고서 | 고유 출처 수, 필수 섹션, 인용 수, 미해결 주장 0, 독립 승인 |
| 콘텐츠 캠페인 | 브리프, 마스터 원문, 채널 패키지, 권리 검토 | 요청 채널 전체, 필요 시 출처, 권리·브랜드 승인, 최종 콘텐츠 승인 |
| IP 사업 기획 | 사업 가설, 시장 근거, 권리 전략, 재무 모델, 사업계획서 | 시장 출처, 필수 섹션, 권리 승인, 재무 산식 승인, 최종 사업 검수 승인 |

교차 검증에서 다음을 확인했다.

- 웹앱은 출처 수가 없어도 테스트·브라우저·코드 검수가 완전하면 통과한다.
- 웹앱의 실패한 명령은 리포트용 출처 근거로 대체되지 않는다.
- 리포트는 테스트 성공이나 브라우저 캡처가 있어도 출처가 부족하면 반려된다.
- 다른 프로젝트의 손상된 실행은 현재 실행의 검수 결과를 오염시키지 않는다.

관련 코드:

- `orchestrator/src/workpacks/builtins/webApp.ts`
- `orchestrator/src/workpacks/builtins/contentCampaign.ts`
- `orchestrator/src/workpacks/builtins/ipBusinessPlan.ts`
- `orchestrator/src/workpacks/builtins/index.ts`

## 결정 기록

**R-WP1 — 현재 TypeScript 코어만 실행 계약을 소유한다.** 이전 Python/LangGraph 엔진을 병행하면 이벤트·중단·복구·검수 의미를 두 번 구현해야 하기 때문이다. 이 결정이 틀리면 Python 전용 도구를 별도 실행 어댑터로 추가하되 상태 엔진은 복제하지 않는다.

**R-WP2 — 실행마다 작업 팩 id/version을 고정한다.** 팩 수정으로 과거 실행의 판정 결과가 소급 변경되는 것을 막기 위해서다. 이 결정이 틀리면 명시적 마이그레이션 레코드가 필요하다.

**R-WP3 — 결정론적 검사를 AI 검수보다 먼저 수행한다.** 종료 코드, 필수 산출물, 출처 수, 채널 목록, 승인 근거처럼 기계가 판단할 수 있는 항목에 모델 비용을 쓰지 않기 위해서다. 이 결정이 틀려도 팩별 검수 함수만 교체하면 된다.

**R-WP4 — 검수 범위를 실행 단위로 격리한다.** 다른 프로젝트의 손상이나 진행 중 데이터가 정상 실행을 반려시키지 않게 한다. 전체 데이터 무결성 검사는 별도 운영 검사로 유지한다.

**R-WP5 — 이전 프로젝트에서는 역할·업무 템플릿만 이식한다.** 검증 실패 결과 자동 완료, 비결정적 명령 성공 판정, API 키 DB 저장 방식은 가져오지 않았다.

**R-WP6 — 실제 모델·외부 API·게시 작업은 호출하지 않는다.** 이번 단계는 계약과 판정 경로 검증이며, 저장소 지침상 실제 Claude/Codex/OpenAI 호출은 별도 확인이 필요하다.

## 검토 및 검증 결과

작업 팩 전용 테스트는 5개 파일, 18개 테스트다. 정상 경로와 다음 실패를 포함한다.

- 관계 누락·중복·교차 실행 참조·의존 순환
- 작업 팩의 중복 태스크·없는 역할·없는 의존
- 필수 산출물·media type 누락
- 웹앱 명령 실패·브라우저 근거 누락
- 리포트 출처·섹션·인용·독립 검증 누락
- 콘텐츠 채널·권리 검토 누락
- IP 시장·권리·재무·최종 검토 누락
- 다른 프로젝트 데이터로 인한 검수 오염

깨끗한 커밋 기준 최종 검증:

- 오케스트레이터 `npx tsc --noEmit`: 통과
- 오케스트레이터 `npm run build`: 통과
- 오케스트레이터 전체 테스트: 38개 파일, 371개 통과
- 대시보드 전체 테스트: 17개 파일, 169개 통과
- 대시보드 빌드: 통과

검증용 임시 Git 작업공간은 결과 확인 후 제거했다. 실제 AI 모델, Telegram, 외부 게시 API는 호출하지 않았다.

## 의도적으로 이번 단계에 넣지 않은 것

- 작업 팩 선택을 CLI·HTTP API·대시보드에 노출하는 UI
- 작업 관계의 영속 저장소와 이전 프로젝트 데이터 마이그레이션
- 비개발 태스크를 실제 에이전트 러너에 할당하는 실행 어댑터
- 콘텐츠 자동 게시, 영상 생성, IP 법률·투자 판단 자동 승인

위 항목은 계약을 검증한 뒤 붙이는 것이 중복 구현 비용이 가장 적다. 특히 법률·재무 결과는 자동 승인하지 않고 사람 검토 게이트를 유지해야 한다.

## 기존 미커밋 변경과의 분리

작업 시작 전부터 `DESIGN.md`와 엔진·HTTP·텔레그램 테스트 파일에 미커밋 변경이 있었다. 이를 이번 커밋에 섞지 않았다.

기본 작업 트리에서 전체 테스트를 한 번 실행했을 때, 그 미커밋 HTTP 방어 코드가 포트 80의 `Origin: http://localhost`를 `http://localhost:80`과 동일하게 처리하지 않아 해당 미커밋 테스트 1개가 실패했다. 작업 팩 커밋만 체크아웃한 깨끗한 임시 작업공간에서는 위 전체 검증이 모두 통과했다. 해당 기존 변경은 손대지 않고 보존했다.
